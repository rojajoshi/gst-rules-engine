# Data Dictionary

What every column in the pipeline means. The machine-readable version is `config/schema.yaml`, and the two must stay in sync. Column names match `docs/rules_spec.md`.

All data in this project is synthetic, generated by `scripts/generate_data.py`. All amounts are assumed to be AUD; foreign currency is out of scope.

## Implementation notes

- **Money** is stored as `Decimal` in Python and `DECIMAL(12,2)` in SQL, never as floats. DuckDB's `.df()` returns decimals as floats, so money calculations happen in Python.
- **Reading CSVs:** always use `keep_default_na=False`, otherwise pandas turns `N/A` (used in `credit_claimable`) and `NA` (Namibia's country code) into blanks.
- **YAML:** quote country codes. An unquoted `NO` (Norway) loads as `False`.

## 1. Transactions (standard schema)

One row per invoice line, after each client's file has been mapped into this format. Only values known from the raw file live here. Anything that depends on GST treatment is an engine output (section 2).

**Business key:** `client_id` + `invoice_id` + `line_no`. This is flagged, not enforced: duplicate lines are kept and reported by the `duplicate_line` check, so the key is only unique after de-duplication.

| Column | Type | Required | Description |
|---|---|---|---|
| `client_id` | string | Yes | Client the file came from, e.g. `client_a` |
| `source_file` | string | Yes | Raw file the row was read from |
| `source_row_number` | integer | Yes | Row number in the raw file, so every result can be traced back |
| `invoice_id` | string | Yes | Invoice number as issued |
| `line_no` | integer | Yes | Line number within the invoice |
| `invoice_date` | date | Yes | Parsed using the client's `date_format` |
| `document_type` | `invoice` / `credit_note` | Yes | Default `invoice`. Credit notes can legitimately be negative |
| `transaction_type` | `sale` / `purchase` | Yes | From the client's point of view |
| `original_supplier` | string | No | Supplier name exactly as received |
| `supplier_id` | string | Purchases | Matched from `original_supplier` via `suppliers.csv`. Blank if no match |
| `description` | string | No | Line description as received |
| `original_tax_code` | string | No | Tax code exactly as received |
| `tax_code` | string | No | Normalised tax code (trimmed, upper case) |
| `amounts_include_gst` | boolean | Yes | Set from the client's mapping config |
| `original_amount` | money | Yes | Amount exactly as received, never overwritten. Inclusive or exclusive per `amounts_include_gst` |
| `gst_charged` | money | No | GST shown on the client's invoice |
| `original_destination` | string | No | Destination exactly as received |
| `destination_country` | ISO 2-letter code | No | Normalised (trimmed, upper case). Blank if missing or not in `countries.csv` |

## 2. Engine outputs

Added by the engine. Never present in raw files.

| Column | Values | Description |
|---|---|---|
| `category` | see Categories | Resolved category |
| `category_source` | `tax_code` / `supplier_default` / `llm` / `unknown` | Where the category came from |
| `rule_id` | e.g. `R01`, `R99` | Treatment rule that fired |
| `gst_treatment` | `taxable` / `gst_free` / `input_taxed` | GST treatment |
| `net_amount` | money | GST-exclusive amount. Derived once treatment and supplier registration are known (e.g. Client B's $110 is $100 net if taxable, $110 if GST-free) |
| `gross_amount` | money | GST-inclusive amount, derived the same way |
| `expected_gst` | money | GST the engine expects, rounded per line |
| `credit_claimable` | `Yes` / `No` / `Review` / `N/A` | Purchases only. `N/A` for sales |
| `gst_variance` | money | `gst_charged` minus `expected_gst`. Blank if `gst_charged` is missing |
| `excluded_from_bas` | boolean | True if the row has any `error`-severity issue. BAS totals only include rows where this is false |

## 3. Categories

| Category | Usual treatment | Rule |
|---|---|---|
| `stationery` | Taxable | R99 |
| `software` | Taxable | R99 |
| `taxable_food` | Taxable | R03 |
| `basic_food` | GST-free | R04 |
| `financial_services` | Input-taxed | R02 |
| `payment_processing` | Taxable | R99 |
| `gst_free_medical` | GST-free | R05 |
| `gst_free_other_health` | GST-free | R05 |
| `cosmetic_procedure` | Taxable | R99 |
| `unknown` | Taxable (provisional, flagged) | R99 |

Exports (R01) override all of these for sales with a valid overseas destination.

## 4. Reference tables

The CSV files are the source of truth for their values. `schema.yaml` only defines their columns, and a test checks every category they use is a valid category.

### `data/reference/suppliers.csv`

| Column | Type | Required | Description |
|---|---|---|---|
| `supplier_id` | string | Yes | Unique key |
| `supplier_name` | string | Yes | Fictional names only. Matched against `original_supplier` |
| `default_category` | category | No | Used when a line has no usable tax code. Ignored when `multi_category` is true |
| `multi_category` | boolean | Yes | Supplier sells across categories, so its default can't be trusted |
| `gst_registered` | boolean | Yes | Unregistered suppliers can't charge GST |
| `country` | ISO 2-letter code | Yes | Supplier's country |

### `data/reference/tax_codes.csv`

| tax_code | category | description |
|---|---|---|
| `ST` | `stationery` | Office supplies and printing |
| `SW` | `software` | Software and licences |
| `TF` | `taxable_food` | Prepared, hot or other taxable food |
| `BF` | `basic_food` | GST-free basic food |
| `FS` | `financial_services` | Input-taxed financial supplies |
| `PP` | `payment_processing` | Payment processing (taxable) |
| `MED` | `gst_free_medical` | GST-free medical services |
| `OHS` | `gst_free_other_health` | GST-free other health services |
| `COS` | `cosmetic_procedure` | Cosmetic procedures (taxable) |

### `data/reference/countries.csv`

Valid ISO 3166-1 alpha-2 country codes (`country_code`, `country_name`), from `pycountry`. Used by the `invalid_country` check. Read with `keep_default_na=False`, since Namibia's code is `NA`.

### `data/reference/planted_errors.csv`

The answer key for tests: every problem deliberately planted by the generator, with the check that should catch it. Rows marked `none` look suspicious but must **not** be flagged.

## 5. Data quality issues

`data/output/issues.csv` has one row per problem: `client_id`, `source_file`, `source_row_number`, `invoice_id`, `line_no`, `check_name`, `severity`, `message`. (The column is `check_name`, not `check`, because `CHECK` is a reserved word in DuckDB.)

| Check | Severity | Meaning |
|---|---|---|
| `missing_required_field` | error | A required column is blank |
| `invalid_date` | error | `invoice_date` couldn't be parsed |
| `duplicate_line` | error | Same business key appears more than once (every copy after the first) |
| `gst_charged_by_unregistered_supplier` | error | Invoice shows GST but supplier isn't registered |
| `possible_resubmitted_invoice` | warning | Different `invoice_id`, same supplier, date and total |
| `missing_supplier` | warning | Purchase with a blank supplier |
| `orphan_supplier` | warning | `original_supplier` not in `suppliers.csv` |
| `unmapped_tax_code` | warning | `tax_code` not in `tax_codes.csv`. Treated as no tax code |
| `unknown_category` | warning | No usable tax code or supplier default. R99 applied provisionally |
| `category_conflict` | warning | Tax code disagrees with a single-category supplier's default |
| `missing_destination` | warning | Sale with blank destination |
| `invalid_country` | warning | Destination not in `countries.csv` (e.g. `Australia`). Export rule skipped |
| `negative_amount_on_invoice` | warning | Negative amount on an invoice (fine on credit notes) |
| `gst_mismatch` | warning | `gst_variance` outside rounding tolerance |
| `amount_outlier` | info | Unusually high for this supplier: modified z-score (median + MAD) above 3.5. Flagged, not invalid |

**`amount_outlier` rules:**
- Only amounts above zero are scored, so a negative amount can't distort the supplier's median and MAD. Negatives on invoices are caught by `negative_amount_on_invoice`.
- Multi-category suppliers are skipped, because mixing their categories in one group means there's no single normal amount to compare against.
- Only unusually high amounts are flagged, because the review is looking for overstated amounts and small ordinary charges would only add noise.

**Severity:**
- `error`: the row can't be trusted until fixed. Sets `excluded_from_bas` = true, so it's **left out of BAS totals** and reported separately
- `warning`: needs a human to check. Still included in totals
- `info`: unusual but probably fine. Still included in totals
